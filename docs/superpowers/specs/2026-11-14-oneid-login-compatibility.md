# OneID OAuth2 login compatibility

Superseded by [general confidential-client OAuth2 compatibility](2026-11-14-confidential-client-pkce-design.md). The following records the earlier scoped release.

OneID's real authorization requests on 2026-11-14 omitted both PKCE fields and were refused before login. A comparison request carrying S256 reached the login page. The user approved an exception only for the existing OneID confidential client; all other clients keep mandatory PKCE.

Add a boot-time `oauth.confidential_login_clients_without_pkce` allowlist. An exception is valid only for active, admin-registered clients with a secret and basic/post secret authentication, the authorization-code grant, an exact HTTPS callback, no resource parameter, and exactly the `oneid:login` scope. Both authorization and code exchange enforce the same boundary. Existing challenges still require the verifier; partial PKCE is refused. Code exchange still authenticates the secret, checks the callback, expiry and user, and atomically consumes the code. An authenticated legacy code replay revokes its grant; a replay without the correct secret cannot trigger revocation.

Add `userinfo.preferred_usernames`, an administrator-controlled map from stable local subject to a login name. Copy configuration before serving. Without configuration, preserve the email-based default. With a configured map, unmapped subjects omit `preferred_username`; they never inherit another subject's username. Validate nonempty bounded strings and unique usernames case-insensitively. Keep `sub`, email and display name unchanged. The server-side mapping for the user's existing local account is reused from the already configured jump-wb bridge; personal mapping values are not hard-coded into service code.

Validation: signed-token HTTP mapping tests; YAML load/validation tests; admission-policy cases; full PKCE and allowlisted non-PKCE code/refresh/revoke flows; code-exchange negative cases and credential-gated replay; full CI and integration tests. An independent review checks boundaries before deployment. Regenerate configuration and HTTP references, push the existing feature branch and deploy a backed-up, versioned image/configuration. Verify public non-PKCE login initiation and complete a non-PKCE flow with the test account; the actual mapped account login requires its user's password.
